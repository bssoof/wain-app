### High

#### H-01 - Config publish/rollback bypasses the intended step-up check

Severity + CVSS-style reasoning: High, CVSS-style 7.1. A valid or stolen `super_admin` admin session can execute highly sensitive config publish/rollback actions without the intended fresh re-authentication; impact is high integrity, while privileges are still required.

Location: `admin_web_console/app/api/admin/command/config/route.ts:48`, `admin_web_console/app/api/admin/command/config/route.ts:137`, `admin_web_console/lib/auth/step-up-required.ts:12`, `admin_web_console/lib/config/config-command-contracts.ts:8-9`

Description: `publish_config` and `rollback_config` are registered as config step-up commands, but the config command API route authorizes the session and immediately builds the callable transport. Unlike the finance route, it never calls `verifyStepUpForCommand({ scope: "config", ... })`.

Evidence:

```ts
// lib/auth/step-up-required.ts
config: ["publish_config", "rollback_config"],

// app/api/admin/command/config/route.ts
const authz = authorizeConfigCommand(session, command);
...
const transport = createConfigCommandAdaptersTransport({
  invokeCallable: createHttpsCallableInvoker({
    baseUrl: callableConfig.baseUrl,
    authToken: callableConfig.authToken,
    appCheckToken: callableConfig.appCheckToken,
  }),
});
```

Impact: An attacker who obtains an active `super_admin` session, or succeeds with browser-side command execution under that session, can publish or roll back wallet feature pricing/config without a fresh password step-up. This weakens the intended protection for high-impact configuration changes.

Remediation: Mirror the finance route pattern in `admin_web_console/app/api/admin/command/config/route.ts`: import `verifyStepUpForCommand`, call it before resolving/using the callable transport for config commands, audit both success and failure, and add a route-level security test proving `publish_config` and `rollback_config` reject missing or invalid step-up cookies.

Effort estimate: Quick (<30min)

#### H-02 - Backend config governance still authorizes `finance_admin`

Severity + CVSS-style reasoning: High, CVSS-style 7.7. A valid `finance_admin` can directly call Firebase config governance functions and mutate/publish/rollback config, bypassing the current web RBAC restriction to `super_admin`; impact is high integrity with required admin privileges.

Location: `functions/src/admin_config.ts:50`, `functions/src/admin_config.ts:77-85`, `functions/src/admin_config.ts:389`, `functions/src/admin_config.ts:564`, `functions/src/admin_config.ts:750`, `functions/src/admin_config.ts:998`, `admin_web_console/lib/auth/guard-api.ts:79`, `admin_web_console/lib/auth/guard-api.ts:118-121`

Description: The admin web guard now restricts config route/capabilities to `super_admin`, but the Firebase callable implementation still defines `ConfigGovernanceRole = "finance_admin" | "super_admin"` and accepts `finance_admin` claims/roles for every config governance callable.

Evidence:

```ts
// functions/src/admin_config.ts
type ConfigGovernanceRole = "finance_admin" | "super_admin";
if (token.super_admin === true || token.role === "super_admin") return "super_admin";
if (token.finance_admin === true || token.role === "finance_admin") return "finance_admin";

export const configPublishDraft = functions.https.onCall(async (data, context) => {
  requireAppCheck(context);
  const access = await requireConfigGovernanceAccess(context);
```

Impact: A `finance_admin` with valid Firebase Auth and App Check can bypass the Next.js admin proxy and call the config callable surface directly, including `configUpsertDraft`, `configReviewDraft`, `configPublishDraft`, and `configRollbackVersion`. This breaks RBAC parity and can alter wallet pricing/config outside the current intended approval boundary.

Remediation: Change the callable-side role model to `super_admin` only for all config governance actions, or split read-only and mutation capabilities explicitly if finance read access is still required. Add emulator/callable tests that assert `finance_admin` is denied on `getAdminConfigGovernanceBundle`, draft upsert/review, publish, and rollback.

Effort estimate: Medium (1-3h)

### Medium

#### M-01 - Legacy admin claims bypass active-admin document checks in Functions and rules

Severity + CVSS-style reasoning: Medium, CVSS-style 6.5. A stale token with legacy `admin=true` or `role=admin` can remain privileged even when `admins/{uid}.active` is false; exploitation requires an admin token but undermines deprovisioning.

Location: `functions/src/shared/admin-auth.ts:57-64`, `functions/src/shared/admin-auth.ts:72-80`, `firestore.rules:10-19`, `firestore.rules:390-391`, `firestore.rules:417-418`, `storage.rules:38-45`

Description: Shared callable admin access returns success immediately for legacy admin claims and only reads `admins/{uid}` if those claims are absent. Firestore and Storage rules similarly accept token-level admin claims without requiring an active admin document. `resolveAdminExecutionRole` then defaults any non-super admin execution role to `finance_admin`.

Evidence:

```ts
if (token.admin === true || token.role === "admin") {
  return { uid, source: "claim" };
}

const adminDoc = await db.collection("admins").doc(uid).get();
if (adminDoc.exists && adminDoc.data()?.active !== false) {
  return { uid, source: "document" };
}
```

Impact: If an admin is deactivated in Firestore but their custom claims are not removed and tokens are not revoked, direct callable/rules access can continue until claims/tokens expire or are explicitly revoked. In functions using `resolveAdminExecutionRole`, this also maps the legacy claim path to `finance_admin` behavior.

Remediation: Require an active `admins/{uid}` document for all admin claim paths, then derive effective roles from the active document and/or strict role claims. Remove or tightly sunset `role="admin"` and `admin=true` broad grants, and add rules/callable tests for inactive users with stale claims.

Effort estimate: Medium (1-3h)

#### M-02 - Menu import OCR accepts unscoped `gs://` input files

Severity + CVSS-style reasoning: Medium, CVSS-style 6.1. An authenticated merchant can submit arbitrary GCS URIs for OCR processing and cost consumption; impact is bounded by service-account/object access and downstream parsing, but the callable input is not scoped to the caller's venue upload path.

Location: `functions/src/menu_import.ts:399-401`, `functions/src/menu_import.ts:1071-1082`, `functions/src/menu_import.ts:1146-1157`, `functions/src/menu_import.ts:2276-2294`, `firestore.rules:220-221`

Description: `createMenuImportJob` stores caller-supplied `inputFiles` after only string normalization, and `runVisionOcrBatch` accepts any URI starting with `gs://`. Firestore rules also allow venue merchants to create/update `venues/{venueId}/menu_import_jobs/{jobId}`, so `input_files` can be injected directly into the job document outside the callable.

Evidence:

```ts
function normalizeInputFiles(value: unknown): string[] {
  if (!Array.isArray(value)) return [];
  return value.map((x) => asText(x)).filter((x) => x.length > 0);
}

const validUris = gsUris.filter((uri) => uri.startsWith("gs://"));
...
lines = await runVisionOcrBatch(normalizedFiles);
```

Impact: A merchant can cause backend OCR work against objects outside the expected `venues/{venueId}/photos/menu_import_*` path. This can create cost/availability risk and, where the backend service can read a referenced object and the OCR text maps into menu candidates, can expose text-derived content across storage access boundaries.

Remediation: Validate `inputFiles` server-side against the configured project bucket and a strict prefix such as `gs://<bucket>/venues/{venueId}/photos/menu_import_`. Limit file count, validate extensions/content type by object metadata where possible, and prevent direct client writes to `input_files` in Firestore rules.

Effort estimate: Medium (1-3h)

#### M-03 - Media purge trusts caller-supplied storage paths after quarantine

Severity + CVSS-style reasoning: Medium, CVSS-style 6.4. A `content_admin` or `super_admin` direct callable caller can bind an arbitrary default-bucket path to a quarantined media asset and later purge it; privileges are high, but integrity/availability impact is broad across Storage.

Location: `functions/src/shared/media-governance.ts:230-232`, `functions/src/shared/media-governance.ts:447-450`, `functions/src/admin_media.ts:467-537`, `functions/src/admin_media.ts:769-822`

Description: Media governance normalization accepts `storagePath` directly from the caller. If no `sourceCollection/sourceDocumentId` is present, reference matching returns zero references. `mediaQuarantineAsset` can create a quarantined asset for that asset key, and `mediaPurgeAsset` later deletes `target.storagePath` from the default bucket after the reference check passes.

Evidence:

```ts
const storagePathRaw = workspaceString(payload.storagePath);
const storagePath = storagePathRaw || derivedStoragePath || null;
...
if (!target.sourceCollection || !target.sourceDocumentId) {
  return { referenceCount: 0, matchedSourcePaths: [] };
}
...
await getDefaultStorageBucket().file(target.storagePath).delete();
```

Impact: A privileged media governance caller can delete Storage objects that were never selected from the media center inventory, including paths outside the intended asset class, if they know the path. This is a direct callable/server-side guard gap rather than a normal UI path issue.

Remediation: Require source binding for quarantine/purge, derive the storage path from the referenced Firestore document or indexed media asset instead of trusting request input, and reject purge if the asset was not discovered through the reference index/media center pipeline. Add callable tests for arbitrary `storagePath` quarantine/purge attempts.

Effort estimate: Medium (1-3h)

### Low

#### L-01 - Transport deep-link handoff lacks scheme and host allowlisting

Severity + CVSS-style reasoning: Low, CVSS-style 3.7. A managed transport partner template can cause the mobile app to launch arbitrary URL schemes; attacker control appears to require partner/admin data mutation, so impact is limited but user-facing.

Location: `functions/src/transport.ts:175-183`, `functions/src/transport.ts:263-270`, `functions/src/transport.ts:413-414`, `lib/features/transport/presentation/widgets/venue_transport_card.dart:298-305`

Description: For `deep_link` handoffs, the backend substitutes values into `deep_link_url_template` and returns it as `handoffUrl`. The Flutter client parses the returned string and launches it externally without validating allowed schemes or hosts.

Evidence:

```ts
let url = template;
for (const [key, value] of Object.entries(replacements)) {
  url = url.split(`{${key}}`).join(encodeURIComponent(value));
}
return url;
```

```dart
final uri = Uri.parse(result.handoffUrl);
final launched = await launchUrl(uri, mode: LaunchMode.externalApplication);
if (!launched) {
  await launchUrl(uri, mode: LaunchMode.platformDefault);
}
```

Impact: A compromised or misconfigured transport partner record could prompt the mobile app to open a phishing URL or unexpected app scheme. It also makes future partner onboarding error-prone because safety depends on data correctness rather than code-enforced policy.

Remediation: Validate partner deep-link templates at write/read time and validate the final `handoffUrl` before returning and before launching. Allow only documented schemes and hosts per partner, and reject `javascript:`, `file:`, `intent:`, and unknown custom schemes.

Effort estimate: Quick (<30min)

#### L-02 - Admin web CSP is report-only/permissive and HSTS is absent in code

Severity + CVSS-style reasoning: Low, CVSS-style 3.5. This is defense-in-depth rather than an immediate exploit because no XSS was found, but the admin console is privileged and current headers do not enforce CSP or code-level HSTS.

Location: `admin_web_console/next.config.mjs:19-28`, `admin_web_console/next.config.mjs:58-62`, `admin_web_console/middleware.ts:7-19`

Description: Both Next config and middleware emit `Content-Security-Policy-Report-Only`, not enforced `Content-Security-Policy`, and allow broad `script-src 'unsafe-inline' 'unsafe-eval' https:`. `upgrade-insecure-requests` appears inside the report-only policy, matching the smoke-test warnings that this directive is ignored in report-only mode. No `Strict-Transport-Security` header was found in the app code.

Evidence:

```js
"script-src 'self' 'unsafe-inline' 'unsafe-eval' https:",
"style-src 'self' 'unsafe-inline' https:",
"connect-src 'self' https: wss: ws:",
...(isProduction ? ["upgrade-insecure-requests"] : []),
...
key: "Content-Security-Policy-Report-Only",
```

Impact: If an XSS is introduced elsewhere, the current CSP will report but not block script execution. Missing HSTS in app code leaves enforcement dependent on Firebase Hosting/custom domain behavior and makes the deployed security posture harder to verify from source.

Remediation: Add an enforced baseline CSP, keep a stricter report-only policy for tuning, remove `upgrade-insecure-requests` from report-only, and emit production-only `Strict-Transport-Security` with an appropriate `max-age`. Reduce `script-src` away from broad `https:` and remove `unsafe-eval` outside development if compatible.

Effort estimate: Medium (1-3h)

## 4. Defense-in-Depth Observations

- Admin session cookies are HTTP-only and secure in production; session verification uses Firebase Admin SDK session cookie verification and defaults revocation checks to enabled.
- Unsafe admin header/env session fallbacks are gated to non-production/development paths.
- `ROUTE_ROLE_PERMISSIONS` and config capabilities in the admin web app now restrict config governance to `super_admin`.
- Finance command routes enforce step-up checks for sensitive finance commands and audit success/failure paths.
- Step-up tokens validate algorithm/type, signature, expiry, scope, subject, and recent auth time; production direct signing-key env use is rejected in favor of Secret Manager.
- Admin command proxy code rejects public privileged auth/App Check token env usage for live production transports.
- `/api/admin/health/config` is guarded to `super_admin` and returns statuses/booleans/config URLs rather than secret values.
- Storage rules enforce server-side media size/type limits for image/video upload classes.
- The exact Gemini keys requested in the scan were not found in tracked in-scope code.
- Flutter API-style calls found in `lib/` use HTTPS/Firebase SDK paths; no plaintext production API base URL was found in the in-scope mobile code.

## 5. Recommendations Prioritized List

1. Add config step-up enforcement to `admin_web_console/app/api/admin/command/config/route.ts` for `publish_config` and `rollback_config`.
2. Align `functions/src/admin_config.ts` with web RBAC by restricting config governance callables to `super_admin` unless a separate read-only role is intentionally designed.
3. Upgrade `admin_web_console` from `next@14.2.5` to the fixed 14.2.x line reported by `npm audit`, then rerun the already-approved pre-deploy validation outside this scan.
4. Require active `admins/{uid}` documents for all admin claim paths in Functions, Firestore rules, and Storage rules.
5. Constrain menu import `inputFiles` to the caller venue's expected Storage bucket/prefix and block direct client edits to `input_files`.
6. Derive media purge storage paths from trusted indexed/reference data rather than request payloads.
7. Add URL scheme/host allowlists for transport deep-link handoff in both Functions and Flutter.
8. Move admin CSP from report-only-only to an enforced baseline, remove `upgrade-insecure-requests` from report-only, and add production HSTS.
9. Add emulator/security tests for direct callable RBAC parity: config, media governance, and inactive admin claim cases.
10. Replace local service-account JSON workflows with Secret Manager/ADC where feasible and keep ignored local secret files out of cloud-sync backups.
